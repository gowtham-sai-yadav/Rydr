# Phase 4 W11 — Android release checklist

**Status:** Handoff document. Every step below needs a machine with the Android
SDK and an account this project does not have.
**Scope:** what has to happen between the committed Capacitor project and an
internal-testing release on Play.

---

## 1. What is done, and what is not

Stated plainly, because the difference matters when someone picks this up.

| | State |
|---|---|
| Capacitor project, Android platform, Gradle config | ✅ committed |
| Static export wired to `webDir` | ✅ `npm run android:sync` |
| App icons (5 densities) + splash (7 configurations) | ✅ committed, generated by script |
| Camera capture, gallery pick | ✅ code complete |
| Status bar, splash dismissal, hardware back button | ✅ code complete |
| Push: permission, registration, token, tap routing | ✅ client complete |
| Push: actually delivering a message | ❌ needs Firebase (§4) |
| Compiled once, run in an emulator | ❌ no SDK on the dev machine |
| Signed AAB | ❌ needs a keystore (§5) |
| Play Console listing / internal track | ❌ needs a developer account (§6) |

The project has never been compiled. Expect to fix small Gradle or manifest
issues on the first build; that is normal for a scaffold that has not been
through a compiler, and it is why this is a checklist rather than a claim.

## 2. Prerequisites

- **Android Studio** (bundles the SDK, platform tools and an emulator image).
- **JDK 21**. Capacitor 8's Gradle plugin does not support JDK 26, which is what
  this development machine happens to have — check `java -version` before
  assuming a build failure is the project's fault.
- `ANDROID_HOME` exported, and `$ANDROID_HOME/platform-tools` on `PATH`.

## 3. First build

```bash
cd frontend

# The API URL is baked in at build time. A build pointing at localhost will
# not reach anything from a phone or emulator — use the staging URL, or your
# machine's LAN address for local testing.
NEXT_PUBLIC_API_URL=https://api.staging.example npm run android:sync

npm run android:open      # opens the project in Android Studio
```

Then in Android Studio: **Run ▸ app** against an emulator or a connected
device.

Two things to check first if the app opens to a white screen:

1. `android/app/src/main/assets/public/index.html` exists. If it does not,
   `cap sync` ran before the export finished — `npm run android:sync` does them
   in the right order.
2. The API is reachable from inside the emulator. `localhost` in an emulator is
   the emulator, not your laptop; use `10.0.2.2` for the host, and the backend's
   `ALLOWED_ORIGINS` has to include the webview origin `https://localhost`.

## 4. Push notifications (Firebase)

The client is complete; this is the missing half.

1. Create a Firebase project and add an **Android app** with package name
   `com.rydr.app` — it must match `appId` in `capacitor.config.ts`.
2. Download `google-services.json` into `frontend/android/app/`.
   **Do not commit it** — it is gitignored deliberately; it identifies the
   Firebase project.
3. Add the Google Services Gradle plugin: `classpath
   'com.google.gms:google-services:4.4.2'` in `android/build.gradle`, and
   `apply plugin: 'com.google.gms.google-services'` at the foot of
   `android/app/build.gradle`.
4. Backend: add an endpoint that stores `(user_id, token, platform)` and call it
   from `registerDeviceToken` in `frontend/src/lib/native/push.ts`. Re-send the
   token on **every app start** — FCM rotates tokens and a stale one silently
   drops messages.
5. Backend: send through FCM wherever `services/notifications.notify` writes a
   row, so push and the in-app feed stay in agreement. The payload must carry
   `entity_type` and `entity_id`; `NativeShell`'s tap handler already routes on
   those.

Until step 4 exists, `initPush` acquires a token and logs it. Nothing breaks.

## 5. Signing

```bash
keytool -genkey -v -keystore rydr-release.keystore \
  -alias rydr -keyalg RSA -keysize 2048 -validity 10000
```

Store the keystore and its passwords in a password manager, **not in the
repository**. Losing it means never being able to update the app under this
package name — Play identifies an app by its signing key, and there is no
recovery path.

Then add a `signingConfigs.release` block to `android/app/build.gradle` reading
the credentials from `gradle.properties` or the environment, and build:

```bash
cd frontend/android && ./gradlew bundleRelease
# → app/build/outputs/bundle/release/app-release.aab
```

## 6. Play Console

1. Create the app: **Rydr**, category *Maps & Navigation* or *Social*, free.
2. Upload the AAB to the **Internal testing** track and add tester emails.
3. Complete the required declarations. The honest answers for this build:
   - **Data collected:** name, email address (account); approximate location
     (home city and coordinates the rider enters themselves); photos and videos
     the rider uploads; app-activity data (rides logged, posts, ratings).
   - **Data shared with third parties:** yes — media is stored on Cloudinary,
     and map tiles/routing/geocoding are requested from OpenStreetMap
     infrastructure, which receives coordinates.
   - **Encrypted in transit:** yes.
   - **Deletion:** there is currently **no in-app account deletion**. Play
     requires a way for users to request deletion. This must be resolved before
     production release — either an in-app delete flow or a documented request
     address. Recorded here rather than discovered at review.
4. Content rating questionnaire — the app carries user-generated content, so
   answer that honestly; the W7 moderation queue is the mechanism to point at.
5. Privacy policy URL is mandatory. One does not exist yet.

## 7. Store listing copy

**Short description (80 chars max):**

> Find the best roads, plan group rides, and log every trip with fellow riders.

**Full description:**

> Rydr is built for motorcycle riders who want a better answer to "where should
> I ride this weekend?" than the fastest route.
>
> **Discover destinations.** Browse scenic spots and ride-worthy roads on a map
> or in a filterable list — by distance from home, terrain, vibe, cost, and
> what suits your bike. Every destination carries ratings, photos and notes
> from riders who have actually been.
>
> **Plan a ride.** Create a group ride, approve who joins, and talk it through
> in a real-time chat for that ride. Rides have a rider limit and a waitlist,
> so nobody turns up to a full group.
>
> **Log what you rode.** Record cost, road condition and photos when you get
> back, rate the destination, and generate a share card for Instagram or
> WhatsApp.
>
> **Keep score.** Weekly and monthly distance, riding streaks, badges, and
> leaderboards for both riders and the most-ridden destinations this month.

**Screenshots needed** (min 2, phone; 1080×1920 or similar):
destination map · destination detail with route · ride detail with participants
· ride chat · feed · profile with stats and badges · leaderboard.

Capture from a device or emulator running against seeded data
(`SEED_ON_START=true`), not against an empty database — empty states make poor
screenshots.

## 8. Version bumping

`android/app/build.gradle` holds `versionCode` (integer, must increase for
every upload) and `versionName` (the human string). Play rejects a duplicate
`versionCode` with an error that does not explain itself, so bump it before
each upload.
